# 建模需求清单与协作流程

版本：1.0 · 2026-09-21 · 面向建模、美术、内容审核和前端人员

## 1. 我们要做什么

我们要让用户在网页上转动眼球、拉近观察、隐藏某一层，并用三个可移动的“切面”看到里面的结构。效果类似把一个由多层材料组成的物体切去一角，而不只是播放一段视频。

**最重要的不是交来一张漂亮渲染图，而是交来一个能拆分、能转动、内部也完整的模型。** 第一轮不需要做复杂动画，先把结构、方向与材质对接成功。

当前网页默认加载 `public/models/eye.glb`，该文件由原程序化演示导出，供沟通交互和美术目标使用，不是建模质量或医学准确度的最终验收标准。后续请交付 GLB；直接替换默认资产时，需按《3D模型数据导出规范》的“默认资产对接约定”核对分组、坐标、材质及标注。

## 2. 给建模人员的需求清单

### 必须交付

- 一个完整眼球，明确标记左眼或右眼；不是只做镜头看到的正面。
- 分开命名的巩膜、角膜、虹膜、睫状体、脉络膜、晶状体、视网膜、玻璃体和视神经。
- 虹膜中间的瞳孔是开口，不是贴在眼白上的黑色图片。程序化 demo 的简化黑色遮光片不是正式拓扑要求。
- 内部可见的组织表面也要做好；隐藏外层时不能只剩外壳或明显破洞。
- 一份 `.glb` 文件，以及可以继续编辑的建模源文件。
- 正面、侧面、内部剖面三张预览；标明与参考资料相比做了哪些简化。
- 文件版本、修改记录、模型和纹理的使用授权。

### 用通俗语言理解技术要求

| 技术说法 | 实际希望你做什么 |
| --- | --- |
| GLB 格式 | 像打包好的行李箱，把模型和图片放在一个文件里，不漏附件 |
| 独立节点 | 各组织仍是单独的零件，不要焊成一个无法区分的整体 |
| 原点与单位 | 给所有版本用同一个中心点和尺子，避免每次更新大小和位置都变 |
| 法线 | 表面的“正面朝哪边”要正确，避免网页上像破洞一样消失 |
| UV | 把图片准确贴到模型的展开方式，虹膜纹理不能拉花或错位 |
| 烘焙贴图 | 把只有建模软件会算的复杂纹理，转成网页能读的图片 |
| 面数预算 | 物体由很多小三角形拼成；不影响轮廓的小细节尽量用图片代替 |
| LOD | 同一个模型做高清、普通、轻量几版，方便以后适配不同设备 |
| 透明材质 | 角膜和玻璃体分开做；透明不等于完全看不见，也不是把所有层都变淡 |
| 闭合壳体 | 像有内外表面的蛋壳，而不是没有厚度的一张纸；切开时更容易表现层次 |

### 第一轮先不用做

真实折射光学、医学仿真、血流模拟、眼睑眨动、疾病变化和自动 LOD 不属于当前 demo。需要时先确定审核标准和预算，再制作相应数据。不要为了未确定的效果额外制作大量动画或超高分辨率贴图。

## 3. 第一份试交包

不要等全部精修完成再交。先提交一份简单但结构正确的试交包：

1. 一份未压缩 GLB，包含巩膜、虹膜、晶状体和视网膜等主要层。
2. 至少一张真实导出的贴图，验证材质链路，而不是全用默认灰色。
3. 一张源软件截图，注明正面、上方、尺寸和版本。
4. 若确认需要动画，再加一段短动画验证，不要一开始交完整长时间线。

前端确认：能加载、方向正确、每个部件可选、材质不丢、切开能看见内部。通过后再投入血管和微观细节制作。

## 4. 文件如何传输

使用双方已有的企业网盘、受控共享盘或项目附件系统。每个版本一个独立文件夹或 ZIP，设置适当的访问权限。大文件不直接塞进代码仓库；需要版本化资产时再评估 Git LFS。

命名例：`eye_right_v001.zip`、`eye_right_v002.zip`。不要覆盖同名旧文件，也不要使用“最终版2真的最终版”。文件夹内至少有 GLB、预览、源文件路径和修改说明。

接收方保留收到的原始包，必要时记录 SHA-256 校验值确认传输完整。上传完成后在任务单记录网盘链接、文件大小、版本号和负责人；不以聊天里的口头“已上传”作为唯一记录。

**网页本地导入不会把文件传到服务器。** 点“导入模型”后，GLB 选一个文件即可；glTF 或 OBJ 要把 `.bin`、`.mtl`、贴图等一起选中。先解压 ZIP，避免同名贴图。当前文件总大小上限 100 MB。

## 5. 对接流程与分工

| 阶段 | 建模 / 美术 | 前端 | 内容审核 | 退出条件 |
| --- | --- | --- | --- | --- |
| 需求确认 | 提供参考、拆分方案、制作范围 | 确认交互、目标设备、预算 | 确认结构名称与左右眼 | 需求清单有明确版本 |
| 低精度试交 | 交试验 GLB 和预览 | 导入、看层级、剖切、试材质 | 检查基本结构关系 | 无基础格式或方向问题 |
| 细节制作 | 纹理、内外表面、必要动画 | 固定灯光和相机对照环境 | 审核形态、文案与示意图片 | 重点视角可接受 |
| 性能调整 | 依据具体瓶颈减面、减贴图或透明层 | 测设备、记录帧耗时与 draw calls | 确认优化未改变关键结构 | 达到双方约定目标 |
| 交付验收 | GLB、源文件、预览、授权、变更记录 | 复测全部交互、归档校验报告 | 签注审核状态 | 清单逐项完成 |

每一轮只指定一个接收人汇总反馈，避免不同人分别要求修改相互冲突的效果。

## 6. 怎样验证文件

### 建模端自检

导出后重新打开导出的 GLB，确认不是只看源文件：图片还在、方向没反、尺寸没变、动画还能动，隐藏巩膜后里面是完整的。把这个结果与导出前截图比较。

### 格式自检

使用 Khronos glTF Validator，在页面中选择 GLB，保存 JSON 报告。Error 必须处理；Warning 不一定代表模型坏了，但要逐项说明。OBJ 没有对应的 glTF 校验，需检查配套文件、法线、材质并在网页回归。

### 前端视觉与交互检查

- 完整、局部剖切三个轴和交集开关都正常。
- 图层隐藏和显示正确，选择某个结构时文字对应。
- 放大时虹膜不模糊，远看时轮廓不锯齿或破裂。
- 角膜和玻璃体不过度发白，不遮挡晶状体和内壁。
- 指定动画可播放、暂停、切换，停止后部件位置合理。
- 桌面鼠标和手机触摸均可转动及缩放，页面不横向溢出。

技术校验和医学审核分开记录。标准校验通过，不表示结构关系或医学文案就一定正确。

## 7. 问题反馈模板

```text
问题编号：EYE-014
模型版本：eye_right_v003.glb
环境：浏览器版本 / 系统 / 设备型号 / 页面尺寸
部件：cornea
复现步骤：导入 -> 局部剖切 -> X=0.20 / Y=0 / Z=0
交集开关：开
实际效果：角膜正面出现大片白色，挡住虹膜纹理
期望效果：角膜保留轻微高光，虹膜纹理仍可分辨
附件：整屏截图 + 同视角源软件截图
影响程度：阻塞 / 重要 / 一般
归因待确认：模型 / 材质 / 灯光 / 浏览器
负责人及目标版本：待分配
复测结果：待填写
```

描述可复现的现象，不只说“看起来不对”。截图保留切面值、相机视角和当前部件，便于前端在同样条件下复测。

## 8. 怎么迭代优化

每一轮都保留上一轮，固定相同相机、灯光、剖切参数和截图尺寸比较。先定位瓶颈再修改，不要同时换模型、灯光、材质和设备，导致无法判断哪项改动有效。

| 网页问题 | 优先检查 | 建模调整 | 前端复测 |
| --- | --- | --- | --- |
| 初次打开慢 | 下载体积、图片尺寸、解码时间 | 删无用资源、减图片、保留轻量首屏版 | 冷加载与热缓存分开测 |
| 转动卡顿 | 面数、材质数、透明层、屏幕像素 | 简化不影响轮廓的几何，减少材质切换 | 同设备比较帧耗时与 draw calls |
| 虹膜糊 | UV 占比、贴图本身、压缩 | 增加重点部位像素占比，不先把所有贴图升成 4K | 近距离固定视角对照 |
| 切口像纸片 | 壳体厚度、内面、缺少封口 | 补内外表面；固定切面可预补面 | 区分几何缺陷和 demo 不封口的功能边界 |
| 结构穿插 / 闪烁 | 共面、重复网格、透明排序 | 清理重叠表面，合理分层 | 调整透明参数后复测不同角度 |
| 颜色偏白 | 环境光、曝光、PBR 贴图、色彩空间 | 先提供正确颜色贴图和参考截图 | 前端先固定灯光，不要求美术盲目涂黑模型 |
| 动画错位 | 原点、父级变换、绑定、未烘焙约束 | 导出前验证绑定及关键帧 | 播放完整循环并切换动画 |

建议节奏：低精度确认 → 材质确认 → 结构与细节确认 → 性能确认 → 最终回归。每轮任务单同时写“要改变什么”和“哪些已通过内容不得改变”。

## 9. 最终接收清单

- [ ] 文件版本、左右眼、单位和审核状态明确。
- [ ] GLB 可独立打开，贴图未丢失；无未经允许的远程资源。
- [ ] 关键组织拆分，名称与约定一致。
- [ ] 完整、侧面、剖切和近距离均有验收截图。
- [ ] 材质与源软件参考一致，允许的差异已有书面说明。
- [ ] 动画范围与循环方式符合约定。
- [ ] 目标手机和桌面的性能数据已记录。
- [ ] 格式验证报告、源文件、变更记录和授权文件齐全。
- [ ] 尚未完成的内容明确标注，不把演示效果当作正式医学模型。
